## Re-enumerated at `origin/main` (1e94c7f, 0.229.0) -- the count is wrong in BOTH directions

The "three paths" were measured at a past moment. Sixteen minors have landed since, the serve path was
split into `seams/`, and #455 touched it directly. Re-measured, whitespace-tolerant, and every hit
accounted for by name.

**Method.** `grep -rnE 'fs\s*::\s*read(\s*\(|_to_end|_to_string)'` over all `*.rs` -- **98 hits**, listing
run to termination. Then a SECOND pass for the shape the first regex structurally cannot see:
`\.\s*read_to_end\s*\(` (the method form, which is not `fs::read_*`) and `(tokio|async_fs|smol)::fs::read`.
The widened pass found **3** `read_to_end` sites, all TCP streams (`open.rs:1217`,
`https_serve.rs:112`, `transport.rs:584`) and **zero** async whole-file reads -- so it added nothing on the
capsule side. That is a result, not an absence: the first regex's denominator happened to be right here,
but it was not right by construction.

Of the 98, the capsule/module-touching non-test sites are **9**, not 3.

## The two the ticket named that are NOT capsule reads

- **`lib.rs:1192`** (was cited as `:1004`/`:1842`-adjacent) -- the **staging-directory recursion**. It stats
  and aborts against `max_total_bytes` BEFORE reading, and re-checks the real read length against the budget
  to close the TOCTOU. Already bounded; not a capsule read. This confirms the ticket's own point about the
  miscited Terraform comment.
- **`lib.rs:2282`** -- `serve_cached_response`, which reads a **JSON-RPC response-cache file**, not a capsule.

## The three that ARE whole-capsule reads and ARE genuinely blocked

All three hand the buffer to a `digstore_compiler` API whose signature is `&[u8]`, so no amount of seeking
in dig-node changes them:

- **`lib.rs:1478`** `serve_local_blocking` -> `serve_blind` -- the guest needs the blob in **wasm linear
  memory**. Irreducible here.
- **`lib.rs:2009`** manifest extraction -> `extract_data_section_blob`.
- **`content_serve.rs:745`** `tip_capsule_backs_its_committed_root` -> `verify_module_root`.

The BLOCKED-on-digs#49 verdict is **correct for these three**, and digs#49 is still OPEN.

## The two the ticket never named -- and they are NOT blocked

The blocked verdict examined the paths that **interpret** the capsule. It never examined the paths that only
**hash** it. These do not parse wasm, do not instantiate anything, and do not need a per-chunk merkle
commitment, because they are computing a digest over opaque bytes:

- **`seams/dig_peer/module_serve.rs:131`** `describe_module` -- reads the whole file to produce
  `sha256(whole)` plus a per-chunk hash list. Its own doc says a `dig.getModuleInfo` "costs a full-file read
  PLUS a SHA-256 of every chunk (#1615/G2) -- real work a ~100-byte peer request can trigger".
- **`seams/dig_peer/module_reshare.rs:297`** `promote_into_cache` -- `fs::read` the staged artifact,
  `sha256` it against the admitted digest, then `fs::write` the same buffer to the tmp path. That is
  ~135 MB resident **and** a full in-memory copy.

**`#1615/G1` already shipped the seeking fix for `read_module_window`, immediately above `describe_module`
in the same file. G2 was left.** This is that sibling.

Incremental SHA-256 gives a **bit-identical digest** to the one-shot call, so neither path's verification is
weakened, relaxed, or deferred -- the same bytes are hashed in the same order against the same expected
value. `sha2::{Digest, Sha256}` is already a dependency and incremental hashing is already used across the
crate. **Zero format change, zero new dependency, not blocked by digs#49.**

## Scope taken

The two hash paths. The three interpretation paths stay blocked on digs#49 and are named as such rather
than silently left. `download.rs:2160` (reading a finalized download back) is a different shape -- its
result is retained in an in-memory `FetchedResource` by design, so streaming the read alone would not lower
the peak; that is a separate design question and is **not** folded in here.
